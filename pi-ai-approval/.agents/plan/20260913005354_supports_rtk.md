# ExecPlan: pi-ai-approval の rtk 対応

## 1. 目的

`pi-rtk-optimizer` によって rewrite 済みの `rtk ...` コマンドを、`pi-ai-approval` が適切にリスク評価できるようにする。

本対応では次の2点を実装する。

1. `rtk ...` をリスク評価向けの意味表現へ機械的に正規化する
2. 正規化できず `rtk ...` が残るケースでも、AI レビュアーが `rtk = 安全` と誤認しないための短い指示を追加する

前提として、`pi-ai-approval` が受け取る `event.input.command` はすでに `pi-rtk-optimizer` による rewrite 後の最終実行コマンドである。

実際に実行される `event.input.command` 自体は変更しない。

---

## 2. 背景

`pi-rtk-optimizer` の rewrite 後は、例えば以下のようなコマンドが `pi-ai-approval` に渡される。

```text
cat package.json
→ rtk read package.json

head -5 src/policy.ts
→ rtk read src/policy.ts --max-lines 5

ls -la
→ rtk ls -la
```

実測でもこのような変換が確認されている。

そのため、現在のリスク評価ルールが通常の

```text
cat
ls
grep
git status
```

などを前提としている場合、rewrite 後の

```text
rtk read
rtk ls
rtk grep
rtk git status
```

を同等に評価できるようにする必要がある。

また `rtk` は読み取り専用ツールではない。

`read` / `ls` / `grep` / `find` のほか、`git` / `pnpm` / `docker` / `kubectl` など変更を伴いうる操作もラップするため、`rtk` 自体を安全なコマンドとして分類してはならない。

---

## 3. 基本方針

実行用コマンドとリスク評価用コマンドを分離する。

```text
event.input.command
        │
        │ actualCommand
        ▼
RTK 正規化
        │
        │ reviewCommand
        ▼
決定論的リスク評価
        │
        ▼
AI レビュー
        │
        ▼
承認 / 確認 / 拒否
        │
        ▼
actualCommand をそのまま実行
```

### actualCommand

Pi が実際に実行するコマンド。

例:

```text
rtk read package.json
```

### reviewCommand

リスク評価しやすい形へ正規化した表現。

例:

```text
<read-file> package.json
```

または、

```text
git status
```

実行に使うことはない。

---

## 4. 重要な不変条件

正規化処理は `event.input.command` を変更してはならない。

禁止:

```ts
event.input.command = normalizedCommand;
```

想定:

```ts
const actualCommand = event.input.command;

const normalization =
  normalizeCommandForRiskReview(actualCommand);

await review({
  actualCommand,
  reviewCommand: normalization.reviewCommand,
});
```

正規化はリスク評価の補助情報に限定する。

承認後に実行される文字列は、AI レビュー時に `actualCommand` として提示したものと一致させる。

---

## 5. 正規化結果のデータモデル

正規化結果は単なる文字列ではなく、状態を保持する。

```ts
type CommandNormalizationResult = {
  actualCommand: string;
  reviewCommand: string;
  status: "unchanged" | "normalized" | "partial";
  containsRtk: boolean;
};
```

### unchanged

RTK を含まず、変換不要。

```ts
{
  actualCommand: "git status",
  reviewCommand: "git status",
  status: "unchanged",
  containsRtk: false,
}
```

### normalized

RTK 操作をリスク評価可能な形へ正規化できた。

```ts
{
  actualCommand: "rtk git status",
  reviewCommand: "git status",
  status: "normalized",
  containsRtk: true,
}
```

### partial

RTK を含むが、一部または全部を安全に正規化できない。

```ts
{
  actualCommand: "rtk unknown-command foo",
  reviewCommand: "rtk unknown-command foo",
  status: "partial",
  containsRtk: true,
}
```

`partial` はエラーとはせず、AI に解釈を委ねる状態とする。

---

## 6. 正規化処理

新しい純粋関数を追加する。

```ts
normalizeCommandForRiskReview(
  command: string
): CommandNormalizationResult
```

責務は以下に限定する。

* RTK 呼び出しを検出する
* 既知の RTK サブコマンドをリスク評価用表現へ変換する
* 全体を正規化できたか判定する
* 実行コマンドは変更しない

RTK 自体の rewrite 処理は実装しない。

---

## 7. 正規化の考え方

「RTK rewrite 前の文字列を完全復元する」ことを目的にしない。

目的は、

> そのコマンドが何をする操作なのかを、既存のリスク評価が理解できる形へ変換する

ことである。

例えば、

```text
rtk read package.json
```

を厳密に

```text
cat package.json
```

へ戻す必要はない。

リスク評価に必要なのは、

```text
package.json を読み取る
```

という意味である。

したがって、RTK 固有操作については評価専用の意味表現を使ってよい。

例:

```text
<read-file> package.json
```

ただし、既存の決定論的評価処理が通常のシェルコマンド文字列を強く前提としている場合は、既存実装との相性を優先する。

---


例:

```text
rtk read package.json
→ <read-file> package.json
```

```text
rtk read src/policy.ts --max-lines 5
→ <read-file> src/policy.ts
```

リスク評価ではファイル読み取りとして扱う。

RTK 固有の表示量制御オプションは、ファイルアクセスリスクに影響しない限り正規化時に除外してよい。

```text

```

例:

```text

→ ls -la
```

---

```text

```

---

```text

```

---


例:

```text

```


## 9. 正規化対象の優先順位

初期実装では以下を優先する。

### Phase 1

今回の実測で頻出しているもの。

```text
rtk read
rtk ls
rtk grep
rtk find
rtk git
```

実際の失敗例でも `read`、`ls`、`grep` が多数を占めている。

### Phase 2

変更系操作を含むもの。

```text
rtk pnpm
rtk docker
rtk kubectl
```

これらについて、`rtk` が付くことで本来の変更リスクが失われないことを保証する。

### Phase 3

実際の利用状況を見ながら対応範囲を拡張する。

全 RTK サブコマンドの網羅は初期目標としない。

---

## 10. 複合コマンド

RTK はコマンド文字列の先頭だけに現れるとは限らない。

実測でも、

```bash
echo hi && rtk ls
```

や、

```bash
grep ... | rtk grep -v node_modules && ...
```

のようなケースが存在する。

したがって、

```ts
command.startsWith("rtk ")
```

だけを前提にしない。

最低限、以下のようなシェル演算子で区切られた部分に RTK が出現するケースを考慮する。

```text
&&
||
;
|
```

ただし、完全な Shell パーサーを独自実装することは本対応の目的外とする。

既存コードに安全なコマンド分割処理が存在する場合は再利用する。

存在しない場合は、

* 確実に認識できる RTK 部分のみ正規化する
* 残った RTK があれば `status: "partial"` とする

という方針を取る。

正規化率100%を目指さない。

---

## 11. 正規化できない RTK

未知のサブコマンドや複雑な構文は無理に推測して変換しない。

例:

```text
rtk foo --bar
```

結果:

```ts
{
  actualCommand: "rtk foo --bar",
  reviewCommand: "rtk foo --bar",
  status: "partial",
  containsRtk: true,
}
```

重要な原則:

```text
unknown rtk
≠
low risk
```

正規化不能であることを理由に allow 側へ倒さない。

---

## 12. AI レビュアーへの入力

AI には必要に応じて、

```text
actualCommand
reviewCommand
```

の両方を渡す。

### RTK を含まない場合

現行プロンプトを維持する。

RTK 対応のためだけに追加コンテキストを入れない。

---

### 完全に正規化できた場合

例:

```text
Command to execute:
rtk git status

Command for risk analysis:
git status
```

AI には `Command for risk analysis` を主として意味評価させる。

同時に、実際に実行される文字列は `Command to execute` であることを保持する。

---

### 正規化できなかった RTK が残る場合

例:

```text
Command to execute:
rtk foo --bar

Command for risk analysis:
rtk foo --bar
```

この場合のみ、RTK 固有の短い指示を追加する。

---

## 13. AI 向け RTK 指示

システムプロンプトの肥大化を避けるため、RTK の詳細仕様やサブコマンド一覧は追加しない。

必要な原則だけを短く伝える。

推奨:

```text
`rtk` is a proxy for other commands and is not inherently safe or read-only.
Evaluate the underlying operation. If an `rtk` command remains after
normalization and its operation is unclear, do not assume low risk.
```

意味としては以下を伝える。

* `rtk` 自体には固定のリスクレベルを与えない
* サブコマンドと引数が表す実質的操作を評価する
* `rtk` は読み取り専用ではない
* 意味不明な RTK 操作を低リスクと推定しない

これ以上の説明は原則追加しない。

---

## 14. AI 指示を入れる条件

RTK 固有指示を常時プロンプトへ入れない。

推奨:

```ts
if (normalization.status === "partial") {
  prompt += RTK_RISK_GUIDANCE;
}
```

完全に正規化済みの場合は、原則として専用説明を不要とする。

例えば、

```text
rtk git status
→ git status
```

まで機械的に落とせていれば、既存ルーブリックの

```text
git status
```

として評価できる。

これにより RTK を使っていないケース、および正常に正規化できたケースでプロンプト増加を最小限に抑える。

---

## 15. 正規化済みでも actualCommand は提示する

AI に `reviewCommand` だけを渡す設計にはしない。

例えば、

```text
Command to execute:
rtk git status

Command for risk analysis:
git status
```

とする。

これにより AI は、

* リスク判断には正規化形を利用できる
* 実際に実行されるコマンドも確認できる

状態になる。

正規化処理にバグがあった場合でも、AI が実コマンドとの差異を検知できる余地を残す。

---

## 16. 決定論的リスク評価との統合

private data 判定など、既存の決定論的評価についても正規化結果を利用する。

ただし、`actualCommand` に対する既存評価を置き換えない。

概念:

```ts
const actualRisk =
  detectRisk(normalization.actualCommand);

const normalizedRisk =
  detectRisk(normalization.reviewCommand);

const deterministicRisk =
  maxRisk(actualRisk, normalizedRisk);
```

つまり、

```text
actualCommand
AND
reviewCommand
```

の双方を評価し、より厳しい結果を採用する。

これにより正規化によって既存の検出能力を落とさない。

現行の private data 判定では、少なくとも以下について RTK rewrite 前後で同じ判定結果が確認されている。

```text
~/.ssh
$HOME/.ssh
~/.aws
```

この既存挙動は維持する。

---

## 17. private data と read

特に、

```text
rtk read ~/.ssh/id_rsa
```

のようなケースは、

```text
<read-file> ~/.ssh/id_rsa
```

へ正規化しても private data と判定できなければならない。

同様に、

```text
rtk grep token ~/.ssh
rtk find ~/.aws -name credentials
```

についても、正規化によってパス情報を失わない。

正規化処理では、

* パス
* URL
* 対象リソース
* 操作対象名

など、リスク判断に必要な引数を極力保持する。

---

## 18. 変更系操作

次のようなコマンドが RTK を経由することで低リスク化しないことを保証する。

```text
rtk git commit ...
rtk pnpm install
rtk docker rm ...
rtk kubectl delete ...
```

正規化後は、

```text
git commit ...
pnpm install
docker rm ...
kubectl delete ...
```

として既存のリスク評価へ流す。

RTK は透明なラッパーとして扱う。

## 22. private data の回帰テスト

以下の既存挙動を維持する。

```text

→ private

→ private

rtk grep token ~/.ssh
→ private

rtk find ~/.aws -name credentials
→ private
```

これらは一次資料でも RTK rewrite 前後で同じ判定となっている。

## 23. 実行コマンド不変テスト

最重要。

入力:

```text
rtk git status
```

正規化後:

```text
reviewCommand = git status
```

でも、

```ts
event.input.command === "rtk git status"
```

が維持されることを確認する。

正規化関数が `event.input` に副作用を与えないこともテストする。

---

## 24. AI プロンプトのテスト

### RTK なし

既存プロンプトから不要な差分が発生しないこと。

### normalized

```text
actualCommand
reviewCommand
```

のみ追加され、長い RTK 説明が付かないこと。

### partial

短い RTK 指示だけが追加されること。

RTK のヘルプ全文やサブコマンド一覧などがプロンプトへ混入しないこと。

---

## 25. ログ / デバッグ

通常ログは増やしすぎない。

既存の debug 相当の仕組みがある場合のみ、以下を確認できるようにする。

```text
actual command
review command
normalization status
```

例:

```text
command normalization:
  actual: rtk read package.json
  review: <read-file> package.json
  status: normalized
```

AI プロンプト全文の追加ログ出力は不要。

---

## 26. 非目標

本対応では以下を行わない。

* `pi-rtk-optimizer` のロード順制御
* `pi-rtk-optimizer` の rewrite 処理の再実装
* RTK rewrite 前のコマンドの完全復元
* RTK の全サブコマンド対応
* 完全な Shell パーサーの独自実装
* `rtk` の一律 allow / deny
* 正規化後コマンドの実行
* `event.input.command` の書き換え
* AI プロンプトへの長大な RTK 仕様追加

---

## 27. 実装順序

### Step 1

`CommandNormalizationResult` と、

```ts
normalizeCommandForRiskReview()
```

を追加する。

---

### Step 2

まず以下を正規化する。

```text
rtk read
rtk ls
rtk grep
rtk find
rtk git
```

---

### Step 3

既存のレビュー処理へ、

```text
actualCommand
reviewCommand
```

を導入する。

実行コマンドは変更しない。

---

### Step 4

決定論的リスク評価を、

```text
actualCommand
reviewCommand
```

の双方に対して行う。

より厳しい結果を採用する。

---

### Step 5

AI レビューへ `reviewCommand` を追加する。

RTK が完全に正規化できる場合、RTK 固有説明は追加しない。

---

### Step 6

`status === "partial"` の場合だけ次の短い指示を追加する。

```text
`rtk` is a proxy for other commands and is not inherently safe or read-only.
Evaluate the underlying operation. If an `rtk` command remains after
normalization and its operation is unclear, do not assume low risk.
```

---

### Step 7

以下を正規化対象へ追加する。

```text
rtk pnpm
rtk docker
rtk kubectl
```

---

### Step 8

複合コマンド内の RTK 正規化へ対応する。

安全に解析できないケースは `partial` にフォールバックする。

---

### Step 9

単体テスト・プロンプトテスト・private data 回帰テストを追加する。

---

## 28. 完了条件

以下をすべて満たしたら完了とする。

* rewrite 済みの `rtk ...` を `pi-ai-approval` が適切にリスク評価できる
* `rtk read` / `ls` / `grep` / `find` / `git` の主要操作を正規化できる
* `pnpm` / `docker` / `kubectl` など変更系操作も元の操作として評価できる
* `rtk` 自体を一律低リスクとして扱わない
* 正規化できない RTK は `partial` になる
* `partial` の場合のみ、短い RTK 向け AI 指示が追加される
* RTK を含まない通常ケースではプロンプト増加がない
* 完全正規化できる RTK では RTK 固有説明を原則追加しない
* AI には `actualCommand` と `reviewCommand` の両方を確認できる形で渡す
* `event.input.command` は正規化処理で変更されない
* private data 等の既存決定論的判定を退行させない
* `actualCommand` と `reviewCommand` の双方を評価し、正規化によってリスクを過小評価しない
* 未知の RTK 操作を自動的に very_low / low と推定しない
