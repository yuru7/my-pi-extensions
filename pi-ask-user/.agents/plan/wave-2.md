# ExecPlan: pi-ask-user のツール選択誘導の最適化

## 1. 目的

`pi-ask-user` のモデル向けプロンプトを最適化し、`rpiv-ask-user-question` と同程度の柔軟な質問判断を、より少ないプロンプトトークンで実現する。

単純に質問回数を増やすのではなく、ユーザーの回答によって実装方針や成果物が実質的に変わる場面で、適切に質問できることを目指す。

### 成功条件

1. rpiv版が想定する4種類の質問場面をすべてカバーする。
2. 作業を進められる場合でも、ユーザーの判断が結果に実質的な影響を与えるなら質問できる。
3. 既存の規約や文脈から判断できる軽微な事項については、不要な質問を抑制する。
4. 関連する質問を1回のツール呼び出しにまとめる。
5. rpiv版よりモデル向けプロンプトのトークン数を削減する。
6. 質問UI、入力検証、回答処理、タイムアウトなど既存機能の互換性を維持する。

- 質問の自動生成・強制呼び出し機構の追加

## 3. 設計方針

### 3.1. 呼び出し判断の基本原則

モデルは次の場面で質問ツールの利用を検討する。

1. ユーザーの好み・要件を確認する場合
2. 曖昧な要件を明確にする場合
3. 実装・設計に関する意思決定を求める場合
4. 代替案や進め方の選択肢を提示する場合

ただし、これらに該当するだけで必ず質問するわけではない。

**ユーザーの回答によって結果が実質的に変わるか**を主要な判断基準とする。

### 3.2. 質問を必須条件に限定しない

以下のような条件を設けない。

- 質問しなければ作業を進められない
- 必要な情報が完全に欠落している
- 合理的な推測が一切できない

合理的な推測で実装可能であっても、ユーザーの判断によって重要な設計・仕様が変わるなら質問を許容する。

### 3.3. 不要な質問を抑制する

以下のような質問は原則として省略する。

- 既存コードや設定から明確に判断できる事項
- 一般的な実装慣習に従えば十分な事項
- 回答による成果物への影響が軽微な事項
- 既にユーザーが回答・指定した事項

ただし、既存の慣習で処理可能な場合でも、重大なトレードオフや不可逆な変更が存在するなら質問を検討する。

### 3.4. プロンプトの責務分離

| 情報 | 配置先 |
|---|---|
| 質問すべき場面 | `promptSnippet` / `description` |
| 質問の必要性の判断基準 | `promptSnippet` / `description` |
| 質問の集約 | 短い指示文 |
| 質問数・選択肢数 | JSON Schema |
| フィールドの形式 | JSON Schema |
| UI固有の操作 | 必要最小限のツール説明 |
| 不正入力の防止 | Schemaおよび実行時検証 |

Schemaに制約があるだけではモデルが必ず正しい入力を生成するとは限らないため、重要な使用方法については削除可否を検証する。

## 4. 実装案

以下の文言を初期候補とする。

### 4.1. DEFAULT_PROMPT_SNIPPET

```ts
export const DEFAULT_PROMPT_SNIPPET =
  "Ask about preferences, ambiguous requirements, design decisions, " +
  "or alternative approaches when user input would materially affect " +
  "the result. Do not require progress to be blocked. Batch questions.";
```

意図：

- rpiv版が対象とする4種類の質問場面を維持する。
- 作業が停止する場面に限定しない。
- 結果に実質的な影響があるかを基準にする。
- 関連する質問をまとめる。

### 4.2. DEFAULT_TOOL_DESCRIPTION

```ts
export const DEFAULT_TOOL_DESCRIPTION =
  "Ask structured questions to clarify requirements, learn user " +
  "preferences, get implementation decisions, or offer alternative " +
  "approaches. Use when user input would materially affect the result, " +
  "even if you could proceed with assumptions. Avoid trivial questions " +
  "and batch related ones.";
```

`promptSnippet` と判断条件を一致させ、相反する指示が生じないようにする。

説明文の重複は意図的なものか、さらに短縮できるかをトークン測定・評価で確認する。

### 4.3. DEFAULT_PROMPT_GUIDELINES

```ts
export const DEFAULT_PROMPT_GUIDELINES: string[] = [];
```

初期実装では空配列を維持する。

検証で重大な問題が発生した場合に限り、問題を修正するための最小限の指示追加を検討する。

### 4.4. JSON Schema

現行の制約を原則維持する。

- 質問数：1〜4問
- 選択肢数：2〜4個
- `multiSelect` の動作
- `preview` の制約
- 予約ラベルの検証
- その他のバリデーション

誘導文言の短縮に伴ってSchemaの説明が不足していることが判明した場合のみ、最小限の修正を検討する。

## 5. 実行ステップ

### Milestone 1：現行実装とベースラインの確認

作業：

1. 対象リポジトリ内の実装位置を確認する。
2. 現在の `guidance.ts` と `registerTool()` の関係を確認する。
3. rpiv版の3つの誘導フィールドを確認する。
4. JSON Schemaに定義済みの制約を整理する。
5. 既存テストと実行コマンドを確認する。
6. 比較対象のコミットSHAを記録する。
7. 各プロンプトの文字数とトークン数を測定する。

測定対象：

- `description`
- `promptSnippet`
- `promptGuidelines`
- JSON Schemaに含まれる説明文
- Piが実際にモデルへ渡すツール定義全体（取得可能な場合）

測定は同一のトークナイザーで行い、文字数とトークン数を混同しない。

完了条件：

- 比較基準が記録されている。
- 変更すべき箇所が特定されている。
- 既存のテストが実行できる。

### Milestone 2：プロンプト最適化

作業：

1. セクション4の実装案を適用する。
2. 呼び出し条件が4種類の質問場面をカバーすることを確認する。
3. 作業停止を質問の必須条件にしていないことを確認する。
4. 不要な質問の抑制条件を確認する。
5. 既存の設定による `guidance.*` 上書き機能を維持する。
6. 文言の重複・矛盾を点検する。

完了条件：

- 誘導文言が更新されている。
- 呼び出し条件の意図が明確である。
- ツールの公開APIと動作仕様を変更していない。

### Milestone 3：静的テストと回帰テスト

追加または更新するテスト：

- 4種類の質問場面を誘導文言がカバーしている。
- 作業停止を必須条件としていない。
- 重要性の低い質問を抑制する意図が含まれる。
- 複数質問の集約が指示されている。
- 設定による誘導文言の上書きが維持される。
- ツール登録が正常に行われる。
- JSON Schemaと実行時検証が維持される。

文字列の完全一致に過度に依存するテストは避け、振る舞いや設定の整合性を優先する。

完了条件：

- 関連テストが成功する。
- 既存機能への明確な回帰がない。

### Milestone 4：モデルによるツール選択評価

実際のモデルで以下の3構成を比較する。

- A：rpiv版の誘導文言
- B：yuru7版の既定誘導文言
- C：今回の提案版

比較時には、可能な限り同じツール名・Schema・実行環境を使い、誘導文言以外の差が評価結果に混入しないようにする。

ツール選択評価では、必要に応じて実際のUIを開かずに呼び出し判定と引数を記録できるテストハーネスを用意する。

#### 評価ケース

| ID | 依頼例 | 期待動作 |
|---|---|---|
| T01 | ダッシュボードを作成して | 表示内容など重要な好みが未確定なら質問 |
| T02 | 曖昧な業務ルールを実装して | 重要な仕様を質問 |
| T03 | 削除機能を追加して | 論理削除・物理削除などの重要な判断を確認 |
| T04 | 複数のアーキテクチャ案から選びたい | 選択肢を提示 |
| T05 | 既存規約が明確なログ処理を追加して | 原則質問せず実装 |
| T06 | 既存のテスト命名規則に従って追加して | 質問せず実装 |
| T07 | APIの軽微なエラーメッセージを修正して | 不要な質問をしない |
| T08 | 認証方式が未決定の新規システムを作って | 重要な方式選択を質問 |
| T09 | 複数の未確定な仕様を含む機能を実装して | 質問を可能な範囲で集約 |
| T10 | 仕様がすべて明示された機能を実装して | 質問せず実装 |
| T11 | ユーザーが明示的に「質問せず進めて」と指定 | 原則として質問せず進める |
| T12 | 一見合理的なデフォルトがあるが、重要なトレードオフが存在する | 必要に応じて質問 |

各ケースには、既存コード・設定・ユーザー指示など必要な文脈を与える。

「質問が必須」「質問が許容される」「質問すべきでない」を事前に区別する。許容ケースでの質問の有無を単純な正誤として扱わない。

#### 評価指標

- 質問すべきケースでの呼び出し再現率
- 質問不要ケースでの誤呼び出し率
- 質問内容の妥当性
- 複数質問の集約率
- ツール引数の検証エラー率
- プロンプトトークン数

可能なら各ケースを複数回実行して結果のばらつきを記録する。

**主要な合格目標：**

- 質問すべきケースの再現率がrpiv版に対して大きく劣化しない。
- 質問不要ケースの誤呼び出し率がrpiv版を上回らない。
- プロンプトトークン数がrpiv版より少ない。
- Schema違反や質問の集約漏れが増加しない。

評価件数が少ない場合には、統計的な同等性を証明したと主張しない。

### Milestone 5：評価に基づく最終調整

評価結果に応じ、誘導文言を必要最小限で修正する。

想定される調整：

| 問題 | 対応方針 |
|---|---|
| 質問が少なすぎる | 質問を必須条件に限定しない表現を強める |
| 不要な質問が多い | 結果への実質的な影響を重視する表現を強める |
| 実装方式を勝手に決める | 重大な設計トレードオフの確認を明示する |
| 質問を連続呼び出しする | 質問集約の指示を補強する |
| ツール引数の検証エラーが増える | Schemaの説明と最小限の指示を補強する |

変更する際には、プロンプト量と質問品質の両方を評価する。

一部のケースだけを改善するために、他のケースに大きな悪影響を与える過剰な指示を追加しない。

## 8. 実行上の制約

- 既存実装を十分に確認するまではコードを変更しない。
- 変更範囲はモデルへの誘導文言に限定することを原則とする。
- 既存の設定ファイル形式と後方互換性を維持する。
- 新たな依存パッケージは原則追加しない。
- プロンプト量だけを最適化し、質問品質を犠牲にしない。
- 実測していない効果を確定事項として扱わない。
- モデル評価を実行できない環境では、その制約を明記して静的テストまでを完了させる。

## 9. 最終目標

rpiv版のように、ユーザーの好み・曖昧な要件・設計判断・代替案の選択について柔軟に質問できる一方で、既存規約や合理的な判断に基づいて自律的に進められる場面では質問を省略できる状態にする。

**質問の必要性を「作業が停止するか」ではなく「ユーザーの回答が結果に実質的な違いをもたらすか」で判断させる。**

その判断に必要な情報だけをモデルに渡すことで、rpiv版より少ないプロンプト量で、同程度以上の実用的なツール選択品質を目指す。
