# pi-sandbox

Pi coding-agent 拡張機能: プロセスレベルのサンドボックス（bwrap / landlock / seatbelt / windows-acl）— ワークスペースのみ書き込み可能、その他は読み取り専用、フェイルクローズ（fail-closed）設計。

## インストール

```bash
# npm からインストール
pi install npm:@yuru7/pi-sandbox

# またはローカルチェックアウトからインストール
pi install .
```

## 動作の仕組み

bash コマンドはプラットフォーム固有のサンドボックスランナーにラップされ、ローカルで生成・実行されます（**パス透過（path transparent）**: ホストのパスがそのまま動作します）。write/edit ツールは実行前にインプロセスの書き込みフェンス（write fence）を実行します。読み取り（read）には制限がありません。

**対象範囲: モデルが発行したタスクのみ。** ご自身が直接入力した `!command` / `!!command`（および RPC の `bash` コマンド）は、本拡張機能が処理しない `user_bash` イベントを介して Pi 自体によって実行されます。これらはユーザー自身のシェルとして実行され、上記のモードによる制限は受けません。Pi の外部で起動したその他のプロセスについても同様です。

| プラットフォーム | ランナー | 仕組み |
|---|---|---|
| Linux | `bwrap`（推奨） | `--ro-bind / /` によるファイルシステム全体の読み取り専用化 + ワークスペースおよびホストの `/tmp` の読み書きバインド |
| Linux | `landlock-run`（フォールバック、パッケージに同梱された事前ビルド済みバイナリ） | Landlock LSM による許可リスト: `/` は読み取り専用、ワークスペース + `/tmp` は書き込み可能 |
| macOS | `sandbox-exec`（組み込み） | Seatbelt SBPL: `deny file-write*` + ワークスペースおよび一時ディレクトリの例外設定 |
| Windows | `windows-acl`（組み込み、`partial` 適用） | 制限付きトークン（Restricted Token）サンドボックス: `WRITE_RESTRICTED` トークン + ワークスペースおよび `%TEMP%` に対する機能 SID（capability SID）の ACL 付与 + Low mandatory 整合性ラベル。**powershell ツールのみ対応**（制限モードでは `bash` は拒否されます） |
| その他 | なし | **フェイルクローズ（fail-closed）**: 制限されたコマンドは常に拒否され、制限なしで暗黙的に実行されることはありません |

### Windows

`windows-acl` ランナーは、整合性レベルを Low に引き下げた `WRITE_RESTRICTED` トークンから制限付きコマンドを起動します。`workspace-write` モードでは、トークンにはワークスペースおよびホストの `%TEMP%` への書き込み権限が付与された機能 SID も保持され、両方のルートに継承可能な `NO_WRITE_UP` ラベルが設定されます。`read-only` モードでは書き込み権限（capability）は一切付与されません。強制適用は**一部のみ（`partial`）**であり、参照実装から引き継いだ3つの構造的な制約があります:

- **NTFS ハードリンクがファイルオブジェクトのエイリアスとなる**: ワークスペース内の許可されたファイルへのハードリンクは、ワークスペース外からも同様に書き込み可能です
- **読み取りは制限されない**: 本拡張機能の他のすべてのランナーと同様に、制限されたプロセスはユーザーが読み取れるすべてのファイルを読み取ることができます
- **他の AppContainer ツールのパッケージ SID でタグ付けされたファイルは読み取れない**: Low 整合性レベルの子プロセスからは読み取れなくなります（復旧するには外部の ACE を削除するかツリーを再インストールしてください）

利用可能なシェルは **`powershell` ツールのみ**です。Windows（Pi >= 1.0.0）では、pi-sandbox は制限された `bash` を `exposure: "hidden"` で登録します。これにより「登録されているが到達不能（registered but unreachable）」な状態となり、モデルから見えず、明示的に指定（`defaultTools`、`--tools`、`setActiveTools()`）してもアクティブ化されません。登録自体を残しているのは意図的な設計です。拡張機能のツールは同名の組み込みツールを隠蔽（shadow）するため、`bash` という名前をこの定義で占有し続けることで、Windows 上で制限のない組み込み `bash` に到達できないようにしています。将来ホスト側で `hidden` の扱いが変更されたとしても、その定義は依然として制限付きの呼び出しをすべて拒否します（フェイルクローズ設計であり、決してプロセスは起動されません）。明示的に `danger-full-access` に切り替えない限り、Windows 上で `bash` が制限なしで実行されることはありません（`danger-full-access` が唯一の回避策であり、他のプラットフォームと同様に直接実行されます）。

既知の制限事項: **`defaultTools` では拡張機能が登録したツールを選択解除できません**（`-name` 指定は組み込みツールのみを削除し、拡張機能のツールは定義側で除外しない限り自動的にアクティブ化されます）。pi-sandbox ではこのための設定を要求しません。Windows では定義レベル（`exposure: "hidden"`）でモデルから `bash` の名前が取り下げられているため、設定で除外する必要はありません。`powershell` がアクティブでない場合（`powershell` ツールが同梱されていない 1.0.0 より前のホスト、または選択から除外されている場合）、`/permission` には `shell: powershell only (not activated)` と表示され、アクティブなリストにまだ `bash` が含まれている場合（旧バージョンのホスト）はアクティブ化時に一度ヒントが表示されます。`{ "defaultTools": ["+powershell"] }`（Pi >= 1.0.0 が必要）を設定することで再度追加できます。

**サポートされる Windows のバージョン範囲。** 本バックエンドが移植元とした上流の設計（deepseek-harness）と同様に、**新しい OS バージョンの下限はありません**。その仕組みは `WRITE_RESTRICTED` トークンと Low mandatory ラベル（いずれもレガシーな API）であり、まさにそれが `mxc`（Windows 11 24H2 以降）ではなくこの方法が選ばれた理由です。本リポジトリでのエンドツーエンド（e2e）検証は **Windows 10 Enterprise LTSC 2019（ビルド 17763.316）** で実施されており、自動 e2e テストスイートおよび手動受け入れチェックリストをパスしています。これより新しいビルドでも動作すると見込まれますが（バックエンドで新しいビルドに依存する部分はありません）、現時点ではまだ検証されていません。なお、上流の*テスト*は Windows Server 2025 で実行されているため、そのテストフィクスチャは古いビルドに移植できません。本パッケージの Windows テストフィクスチャは、意図的にバージョン非依存のプリミティブを使用しています。

PowerShell の言語モードは ACL の境界ではなく、起動時の制約に従います。`read-only` では `%TEMP%` が書き込み不可となるため、PowerShell は ConstrainedLanguage に低下する場合があります（`Add-Type`/COM/リフレクションが失敗します）。`workspace-write` では FullLanguage が維持されます。

**`NUL` は両モードで書き込み可能です** — これはデバイスの環境プロパティ（DACL で Everyone に読み取り/書き込み/実行が付与されています）であり、機能（capability）の付与によるものではないため、トークンにどのルートが付与されているかに関係なく維持されます。アクセスできるのはデバイスの表記（`cmd` の `> NUL` や Node の `\\.\NUL`）のみです。*相対パス*の `NUL` はデバイスとはみなされません。libuv は NT パスを構築し Win32 デバイス名マッピングを適用しないため、`writeFileSync('NUL', …)` は子プロセスのカレントディレクトリ（cwd）にある `NUL` という通常ファイルとなり、他のファイル名と同様にワークスペース内では許可され、ワークスペース外では拒否されます。

**持続的なセキュリティ記述子の変更。** 付与はべき等（idempotent）ですが、取り消されることはありません。Pi が終了した後も、ワークスペースおよび `%TEMP%` 上の ACE、全ユーザーに対する `FILE_DELETE_CHILD` 拒否（deny）、および Low mandatory ラベルはそのまま残ります。これにより、同一ユーザーとして実行される**すべての** Low 整合性プロセスに対してそれらのツリーが緩和されます。また、後から継承可能なラベルをクリアしても、すでに子オブジェクトに伝播した内容は巻き戻されません。`read-only` に切り替えると機能 ACE は不活性化されますが（そのトークンには機能 SID が含まれないため）、削除されるわけではありません。最初の付与時には `%TEMP%` ツリー全体に積極的に伝播するため（大きなツリーでは数秒かかります）、以降の呼び出しでは完全一致の高速パスが使われます。`%TEMP%` および `TMP` 自体のパスは**書き換えられません** — サンドボックスの書き込み可能な一時ルートはホストの `%TEMP%` です。

**`%TEMP%` に関する影響。** `%TEMP%` は共有ユーザーツリーです。そのサブディレクトリは deny ACE を継承するため、自身のテンポラリサブディレクトリを `GENERIC_ALL`/`FullControl` で開こうとするサードパーティ製アプリケーションは拒否されます。DELETE による削除、`MAXIMUM_ALLOWED`、および通常の読み取り/書き込みオープンには影響しません。

**拒否の分類判定は英語のみ対応しています。** ツールが `[sandbox: …]` という拒否マーカー、エスカレーションヒント、および拒否台帳（ledger）を挿入するためにマッチングする拒否メッセージ表現は、子プロセスの **stderr** に対する英語の Win32/`cmd`/PowerShell メッセージテキストです。日本語版などのローカライズされた Windows ではこれらのメッセージが翻訳されるため、サンドボックスはアクセスを拒否するものの（適用の仕組み自体は言語に依存しません）、ツールが拒否を注記できず、拒否先行（denial-first）のエスカレーションが準備されない場合があります。マーカーが見当たらない場合は、制限の失敗ではなく分類判定の制約として扱ってください。

`koffi`（Win32 呼び出し用の FFI レイヤー）は通常の依存関係ですが、遅延読み込みされ、Windows 上でのみ読み込まれます（Win32 バインディングテーブルが他のプラットフォームで実体化されることはありません）。

同梱されている `diagnose-windows-sandbox-acl` スキル（Windows のファイルアクセス許可によって pi-sandbox の付与がブロックされているケースを診断・修復するスキル）は、**Windows 上でのみ** Pi に提供されます。この修復処理はセキュリティ記述子を変更するため、制限のない呼び出し元を必要とします。承認された `danger-full-access`（または手動）から実行してください。

## 3つのパーミッションモード

| モード | ファイルへの影響 |
|---|---|
| `read-only` | `/dev/null` のみ書き込み可能 |
| `workspace-write`（デフォルト） | 作業ディレクトリ + `/tmp` + `os.tmpdir()` が書き込み可能、その他はすべて読み取り専用 |
| `danger-full-access` | サンドボックスを完全にバイパス（明示的なエスケープハッチ） |

ネットワークは常に許可されます（ネットワーク分離はありません）。

## /permission コマンド

- `/permission` — 現在のステータス（モードとソース、選択されたランナーと適用レベル、ワークスペース）を表示
- `/permission <read-only|workspace-write|danger-full-access>` — モードを**プロセス全体**で切り替え。親セッションおよびすべてのサブエージェント子セッションにおける次回のツール呼び出しから即座に適用されます

## エスカレーション承認（モデル主導、拒否先行）

bash/write/edit は2つのオプションパラメータを受け取ります: `sandbox_permissions`（`workspace-write` または `danger-full-access`）+ `justification`（1文の理由）。承認は**拒否先行（denial-first）**です:

- より広い権限を求めるリクエストは、そのセッションで**同じ操作に対する未消費のサンドボックス拒否記録**（エスカレーション用の引数を除き、同一ツール、同一 cwd、同一の引数）がある場合にのみ処理されます。`echo a` の拒否によって `echo b` が許可されることはなく、bash の拒否によって powershell が許可されることもありません。そうでない場合、エスカレーションパラメータは**無視**され、現在のモードで実行され、結果には `[sandbox: escalation fields were ignored …]` という注記が含まれます。
- 拒否記録は**1回のみ消費**され、10分で失効します。1回の拒否につき、エスカレーションの再試行が正確に1回可能になります（承認はその1回の呼び出しにのみ適用されます）。
- プレースホルダーのパラメータはフィールドごとに正規化されます。省略と JSON の `null` はいずれも「リクエストなし」を意味し、パラメータスキーマは `null` を明示的に宣言しています。これにより、strict スキーマのプロバイダ上のモデル（Pi が両方のフィールドを必須とマークする環境）でも有効な「エスカレーションなし」の値を送信できます。`justification` 内の `"null"` や空文字列も同様に正規化されます。文字列のプレースホルダー（`"null"` / 空文字 / 空白のみ）にはさらにもう1層の保護があります。ツールの `prepareArguments` は、Pi が引数を検証する**前**にこれらを除去します。strict スキーマのモデルは必須かつ任意のフィールドに文字列 `"null"` を設定することがよくあり、この仕組みによってサンドボックスとは無関係なエラーで失敗することなく呼び出しを継続できます。

その1回の再試行を誰が決定するかは `approvalMode` で指定します:

| モード | 動作 |
|---|---|
| `human` | **1回のみ許可（Allow once） / 拒否（Deny）**。Deny の後は任意の理由を入力できます。サブエージェントのリクエストは親のプロンプトに転送されます（インプロセスの pi-subagents、親に UI が必要）。転送チャネルがない場合（ヘッドレス、別プロセスのサブエージェント）、エスカレーションは拒否されます。 |
| `auto-review`（デフォルト） | 独立したレビュワーモデルが `ALLOW` または `DENY` を回答します。レビュワーや UI が利用できない場合も含め、人間へのプロンプトは表示されません。ヘッドレスセッションとサブエージェントセッションでも同じパスが使われます。 |
| `allow-all` | 拒否記録に裏付けられた正当な、より広い権限のリクエストが1回のみ承認されます。これによりセッションが `danger-full-access` に切り替わるわけでは**ありません**。 |

`allow-all` および `auto-review` でも、一致する拒否記録のないリクエストは引き続き拒否されます。不正な `approvalMode`、レビュワーモデル、または思考レベルが指定された場合はエスカレーションが拒否されます。不正な設定によって `allow-all` になることは決してなく、通常の呼び出しに対するサンドボックスは維持されます。

## 自動レビュー（Auto-review）

レビュワーは独立したモデル呼び出しです。エージェントの会話履歴（transcript）は参照せず、ツールは付与されず、エージェントのモデルや思考レベルを変更することもありません。プロンプトに含まれるのは以下のみです:

- サンドボックスのメタデータ（バックエンド、モード、ワークスペース、書き込み可能なパス。ネットワークは許可されたままです）
- 試行されたコマンドまたは書き込みパス、cwd、終了コード、および stdout/stderr の末尾（それぞれ 8KiB）または書き込みフェンスのエラー
- 要求されたモードとエージェントによる理由（justification）

これらのフィールドはレビュワープロバイダの API に送信されます。これはコマンドおよびキャプチャされた出力の開示となる点にご留意ください。シークレット情報のマスク処理は一部の明確なパターンに対してのみ行われます。過度に依存しないでください。

レビュワーは正確に `ALLOW` または `DENY` と回答する必要があります。それ以外の回答（空、混在、ツールの呼び出し）は拒否（deny）として扱われます。通常の `DENY` は確定であり、pi-sandbox が2つ目のモデルに問い合わせたり、人間のプロンプトへフォールバックしたりすることはありません。

`autoReview.model` には `CURRENT`（エスカレーションが処理される時点のエージェントモデル）または `provider/model-id` を指定します。`autoReview.thinkingLevel` には `CURRENT` または Pi の思考レベル（`off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`）を指定します。モデルがサポートしていないレベルを明示的に指定すると、その試行は失敗します。暗黙的にレベルが下げられることはありません。

設定されたモデルを呼び出せない場合（不明な ID、認証情報の欠落、認証失敗、未サポートの API や思考レベル、接続/API/レートリミットのエラー、または15秒のタイムアウト）、pi-sandbox は1度だけ警告を発し、現在アクティブなエージェントモデルと同じ思考設定でレビューを再試行します。各試行にはそれぞれ15秒の制限時間が設定されています。タイムアウトした試行からの遅延レスポンスは無視されます。3つ目のモデルはありません。設定がすでに `CURRENT` であるか、同じプロバイダおよびモデル ID である場合、再試行はスキップされます。その2回目の呼び出しも失敗した場合、エスカレーションは拒否されます。

```text
[pi-sandbox] Auto-review warning:
Configured reviewer model "provider/model-A" is unavailable (request failed).
Falling back to the active model "provider/model-B".
```

警告は、UI が存在する場合は `ctx.ui.notify(..., "warning")` に、存在しない場合は stderr に出力されます。モデル名と簡単な理由が示されます。コマンド、ログ、認証情報は含まれません。警告の表示に失敗しても、判定が許可に変わることはありません。

これはリスクの評価であり、完全な保証ではありません。`danger-full-access` はその1回の呼び出しに対してサンドボックスを解除するため、レビュワーは拒否された単一のパスだけでなく、コマンド全体を評価する必要があります。通常のインストールコマンドであっても、任意のパッケージスクリプトが実行される可能性があります。

## 設定

グローバル設定ファイルは、`getAgentDir()` で取得される Pi のエージェントディレクトリ（通常は `~/.pi/agent`、環境変数 `$PI_CODING_AGENT_DIR` が設定されている場合はそのパス）に配置されます。本拡張機能に手動で作成した `~/.pi/agent` パスを指定しないでください。現在の Pi では、SDK の `agentDir` オプションは拡張機能のコンテキストから参照できません。プロセスで別のエージェントディレクトリを使用する場合は、`PI_CODING_AGENT_DIR` も設定してください。

プロジェクト設定ファイルは `<project>/.pi/` に配置されます。設定ファイルが自動生成されることはなく、既存の古いファイルもそのまま残されます。

フィールドごとの優先順位（後ろの方が優先）:

1. `<project>/.pi/pi-sandbox.json`
2. `<project>/.pi/sandbox.json`（レガシーなファイル名、現在も読み込まれます）
3. `<agent-dir>/pi-sandbox.json`
4. `<agent-dir>/sandbox.json`
5. デフォルト設定

`autoReview.model` と `autoReview.thinkingLevel` は個別にマージされます。信頼されていないプロジェクト、または `isProjectTrusted()` を判定できないホストでは、承認設定を変更できません。mode、runner、probe はマージされますが、`approvalMode` / `autoReview` はグローバル設定ファイルの値が維持されます。これにより、信頼できないリポジトリのチェックアウトによって `allow-all` が選択されるのを防ぎます。

```json
{
  "mode": "workspace-write",
  "runnerCommand": null,
  "runnerFailureSignatures": null,
  "probeTimeoutMs": 5000,
  "approvalMode": "auto-review",
  "autoReview": {
    "model": "CURRENT",
    "thinkingLevel": "CURRENT"
  }
}
```

| フィールド | デフォルト値 | 備考 |
|---|---|---|
| `mode` | `workspace-write` | デフォルトのパーミッションモード。不正な値の場合は警告を表示してデフォルト値にフォールバックします |
| `runnerCommand` | `null` | カスタムの bwrap 互換ランナー引数配列（argv）（次のフィールドとのペア指定が必須） |
| `runnerFailureSignatures` | `null` | カスタムランナーの致命的な診断シグネチャ（空でない単一行文字列） |
| `probeTimeoutMs` | `5000` | ランナーの機能確認プローブのタイムアウトミリ秒（正の整数） |
| `approvalMode` | `auto-review` | `human`、`auto-review`、または `allow-all`。不正な値の場合はエスカレーションを拒否します |
| `autoReview.model` | `CURRENT` | `CURRENT` または `provider/model-id` |
| `autoReview.thinkingLevel` | `CURRENT` | `CURRENT` または Pi の思考レベル |

`/permission` は、実際に使用される承認モードを表示します（プロジェクトが信頼されていない場合はグローバル設定の値）。

## セキュリティに関する注意事項

- 制限されたプロセスは、ホスト上でユーザー自身が**読み取り可能なすべてのファイル**（`~/.ssh` などを含む）を読み取ることができます — これは本サンドボックスの設計上の仕様です（deepseek harness と同様）。root 専用ファイルはファイルアクセス権によって保護されたままです
- bwrap の下では、bash の `/tmp` は**ホストの `/tmp` そのもの**です（write/edit フェンスや landlock/macOS ランナーと同様に rw バインド）。制限されたコマンドは、稼働中のセッションソケットや Pi 自体の一時ファイルを含む、ホストの一時ファイルを変更または削除できます。ホストの `/tmp` のパーミッションがそのまま適用されます。ホストの `/tmp` が書き込み不可の場合、サンドボックスの一時ディレクトリも書き込み不可となります
- Windows では、サンドボックスの一時ルートはホストの `%TEMP%` です（`windows-acl` ランナーは実際のパスに対する権限を付与し、`TMP`/`TEMP` を書き換えません）。制限されたコマンドは、そこにあるホストの一時ファイルを変更または削除できます — 上記の bwrap バインドと同様に「ホストの一時ディレクトリ＝サンドボックスの一時ディレクトリ」という動作になります
- 制限された子プロセスは `LC_MESSAGES=C` を強制します（拒否診断メッセージの分類判定を維持するため）。ユーザーの `LANG`/`LC_CTYPE` には影響しません
- 制限された bash は独自のプロセスグループで実行されます（detached）。タイムアウトや中止（abort）時にはグループ全体が終了されますが、Pi 自体が強制終了（SIGKILL など）された場合、コマンドによって起動されたバックグラウンドの孫プロセスが残る可能性があります（Pi 内部の子プロセス追跡 API は拡張機能からは利用できません）
- landlock のフォールバックは、古いカーネル ABI では一部のみの適用（partial enforcement）となります（ステータス出力にその旨が表示されます）

## pi-container-sandbox 1.x からの移行

- 以前の設定ファイル（エージェントディレクトリおよび `<project>/.pi/` 内の `sandbox.json`）は引き続き読み込まれます。新しい設定は同じディレクトリ内の `pi-sandbox.json` に記述してください。従来の `image`/`runtime`/`host` セクションは警告付きで無視されます。必要に応じて上記の設定フィールドに書き直してください。既存のファイルが削除または上書きされることはなく、ファイルが存在しない場合に自動作成されることもありません
- コンテナランタイム（docker/podman）、イメージビルド、`runtime.mounts`、`/sandbox` コマンド、`--container*` フラグ、および外部パスの承認フローは本パッケージには含まれません
- コンテナレベルの分離（独立したファイルシステム/ネットワーク名前空間）が必要な場合は、`@yuru7/pi-container-sandbox` をインストールしてください（コンテナ実装が維持されています）
- `pi-sandbox` と `@yuru7/pi-container-sandbox` は**排他利用**です。両方が `bash`/`write`/`edit` を乗っ取り、両方が `sandbox.json` を読み込みます（スキーマに互換性はありません）。同時に有効化せず、切り替える前に一方をアンインストールまたは無効化してください。なお、本パッケージはコンテナパッケージが読み込まない `pi-sandbox.json` も読み込みます

### ローカルビルドでのエスカレーション転送の検証

親セッションは `pi -e <path>` を使ってローカルの pi-sandbox を読み込むことができますが、**`-e` は親セッションにのみ影響します**。pi-subagents は各子セッションに対して個別のリソースローダーを構築するため、子セッションは `agentDir` およびプロジェクトの `.pi/` から拡張機能を**再検出**します。もし `~/.pi/agent/settings.json` にまだ `npm:@yuru7/pi-sandbox` が宣言されている場合、子セッションは公開版ビルドを読み込み、転送は**何のエラーも出さずに失敗します**（子セッションは `requires approval, but no approval channel is available` とだけ報告します）。両側で同じビルドが検出されるように設定してください:

```bash
AG=$(mktemp -d); cp ~/.pi/agent/auth.json "$AG/" 2>/dev/null || true
cat > "$AG/settings.json" <<EOF
{ "packages": ["<repo>/pi-sandbox", "<repo>/pi-subagents"] }
EOF
cd <writable project dir> && PI_CODING_AGENT_DIR="$AG" pi
```

観察結果および検証記録は `docs/superpowers/specs/2026-09-30-escalation-approval-forwarding-design.md` §11 に記載されています。
