# ExecPlan: Pi Advisor Extension の実装

## 1. 目的

Pi Coding Agent向けのAdvisor拡張機能を自身のリポジトリに実装する。

参考実装は `@juicesharp/rpiv-advisor` とし、同等の機能性を維持しながら、Executor側のシステムプロンプトに追加されるトークン量を削減する。

**最優先事項はAdvisor呼び出し精度の維持である。**

プロンプト削減のために、Advisorを呼び出すべき場面で呼び出さなくなることは原則として許容しない。

### 参考実装

- Repository: https://github.com/juicesharp/rpiv-mono
- Package: `packages/rpiv-advisor`
- 調査時のバージョン: `2.13.8`
- ライセンス: MIT
- 仕様: `README.md`、`docs/configuration.md`、`docs/tool-reference.md`
- 主要実装: `advisor/register.ts`、`advisor/execute.ts`、`advisor/context.ts`、`advisor/handlers.ts`

実装開始時に参考実装のコミットSHAを記録し、そのバージョンを比較基準とする。

## 2. 成功条件

以下をすべて満たすこと。

1. `rpiv-advisor` の主要機能を再現する。
2. Executorが重要な判断を行う前、行き詰まったとき、完了を宣言する前などにAdvisorを適切に呼び出せる。
3. `standard` モードで元実装よりシステムプロンプトのトークン使用量を削減する。
4. 元実装と比較して、必要なAdvisor呼び出しの再現率を低下させないことを目標とする。
5. Advisor無効時にはツール定義と関連ガイダンスをシステムプロンプトから除外する。
6. 設定を `~/.pi/agent/<extension_name>.json` に保存し、セッションをまたいで復元できる。
7. 標準Pi環境で動作する。参考実装が利用するフォーク版SDKへの依存は必須としない。
8. 既存の拡張機能やツールに悪影響を与えない。

- 別モデルへのAdvisorリクエスト

- Advisor結果のツール結果としての返却
- キャンセル・APIエラー・空応答への対応
- モデル・思考量に応じた動的有効化
- システムプロンプトの最適化
- ユニットテスト・統合テスト・品質比較テスト

追加モードを将来的に導入できる構造にはするが、今回の実装・品質評価対象は `standard` とする。

## 4. 設計原則

### 4.1 呼び出し精度を優先する

プロンプトの文字数削減だけを目的としない。

Advisorを呼び出すべき状況をExecutorが認識できることを重視する。

以下の意味を持つ指示は維持する。

1. 本格的な作業や重要な方針決定の前にAdvisorへ相談する。
2. 作業完了を宣言する前にAdvisorへ相談する。
3. 行き詰まり、繰り返すエラー、方針転換時に相談する。
4. 複数ステップのタスクでは、方針決定前と完了前の相談を基本とする。
5. Advisorの助言を重視し、実測結果や一次情報との矛盾がなければ尊重する。
6. 取得済みの根拠と助言が矛盾する場合、必要に応じて再相談して判断を整理する。
7. Advisorの重要な助言は、次のユーザー向け応答で共有する。

元実装に存在する例外条件も維持する。

- 単なるファイル探索や情報取得などの準備作業では、毎回相談する必要はない。
- ツールの結果から次の行動が明白な短い作業では、不要な再相談を避ける。
- 完了前のAdvisor呼び出しに先立ち、成果物をファイル保存などにより永続化する。

### 4.2 行動指針を過度に削除しない

`standard` モードでは、元実装の行動指針を単純に削除する方法を採用しない。

次の順序で最適化する。

1. 重複する説明を削除する。
2. 冗長な文章を簡潔に書き換える。
3. ツールの機能説明と行動指針を分離する。
4. 同じ指示を複数のプロンプト領域に重複させない。
5. 行動判断に必要な条件と例外は保持する。
6. 品質比較テストで呼び出し精度を確認する。
7. 精度が低下する場合は、必要な指示を復元する。

### 4.3 Advisor専用プロンプトを分離する

Advisor自身の役割、判断方法、回答形式などの詳細な指示は、Advisor API呼び出し時にのみ使用する。

Executorのシステムプロンプトには含めない。

Advisorの出力は原則として以下のいずれかとする。

- Plan: 具体的な実行計画
- Correction: 判断や実装方針の修正
- Stop: 作業停止またはユーザーへの確認推奨

Advisorは読み取り専用の助言者とし、ツールを実行しない。

### 4.4 不要時の常駐コストを排除する

Advisorが未設定・無効・対象Executorモデルで禁止されている場合、`advisor` ツールを有効ツールセットから除外する。

これによって、そのツールの説明および関連ガイダンスがExecutorのシステムプロンプトに含まれないようにする。

## 5. 設定仕様

### 5.1 設定ファイル

配置先：

`~/.pi/agent/<extension_name>.json`

`<extension_name>` は実装先リポジトリで使用する拡張機能名に置き換える。

例：拡張名が `pi-advisor` なら `~/.pi/agent/pi-advisor.json`。

- Piのエージェントディレクトリ配下に保存する。
- XDG設定ディレクトリは使用しない。
- ファイルが存在しない場合は既定値を使用する。
- JSONが不正な場合は警告し、安全な既定値にフォールバックする。
- 書き込み時は既存の未知の設定項目を不用意に削除しない。
- 書き込み失敗時はメモリ上の設定と有効ツール状態を変更しない。
- 可能な限り一時ファイルとリネームによる安全な書き込みを行う。
- POSIX環境ではファイル権限 `0600` を基本とする。

### 5.2 設定項目

初期仕様：

| キー | 型 | 既定値 | 説明 |
|---|---|---|---|
| `model` | string | なし | Advisorのモデル |
| `effort` | string | なし | Advisorの思考量 |
| `promptMode` | string | `standard` | プロンプトモード |
| `disabledForModels` | array | `[]` | Advisor無効化対象 |
| `toolInventory` | string | `full` | Advisorへ送るツール情報 |
| `guidance` | object | 既定の指示 | プロンプトのカスタマイズ |

`model` は原則として `provider/modelId` 形式とする。

`effort` はモデルが対応する思考量のみ選択可能とする。

`disabledForModels` には次の形式を認める。

- `"provider/modelId"`：常に無効化
- `{ "model": "provider/modelId", "minEffort": "high" }`：指定思考量以上で無効化

`toolInventory` は将来の最適化を考慮して以下を定義する。

- `full`：登録済みの全ツールの説明とパラメータスキーマ
- `active`：現在有効なツールのみ
- `names`：ツール名のみ

既定値の `full` は元実装と同等の情報量を保持する。

`guidance` では `promptSnippet`、`promptGuidelines` を上書き可能とする。

`/advisor` の設定変更時にも、これらの手動設定が保持されるようにする。

## 6. 機能要件

### 6.1 advisor() ツール

ツール名：`advisor`

パラメータ：空オブジェクト

Executorが引数なしで呼び出せること。

ツール実行時には以下を行う。

1. 現在のAdvisor設定を取得する。
2. 選択されたモデルを解決する。
3. Piの認証情報を取得する。
4. 現在の会話分岐を取得する。
5. Advisorへ送るツール情報を構築する。
6. 会話履歴をAPI互換の形式に整える。
7. Advisor専用システムプロンプトを設定する。
8. 選択されたモデルと思考量でAPIを呼び出す。
9. 結果をExecutorへツール結果として返す。

Advisorの応答をExecutorの会話履歴へ独立したユーザー発言として追加しない。

### 6.2 会話履歴の処理

元実装と同様に、現在の会話分岐を解決して使用する。

利用可能な場合は次のAPIを参考とする。

- `buildSessionContext()`
- `convertToLlm()`
- `ctx.sessionManager.getEntries()`
- `ctx.sessionManager.getLeafId()`

次の条件を満たすこと。

- 過去のツール呼び出しと結果を含める。
- コンパクション済み要約を反映する。
- 現在の会話分岐だけを対象とする。
- 実行途中の `advisor()` 呼び出しを除外する。
- 孤立したツール呼び出しを作らない。
- 必要に応じて会話末尾をuserメッセージにする。
- Advisor側でExecutorのツールが呼び出し可能にならないようにする。

Piのバージョンごとのsystemメッセージやツール宣言形式の違いにも対応する。

### 6.3 Advisorの実行

可能な限りPiの標準SDKを使用する。

- モデルレジストリでモデルを解決する。
- Piが管理する認証情報を再利用する。
- OAuth認証モデルに対応する。
- 対応する思考量を送信する。
- `AbortSignal` を伝播する。
- Advisorには `tools: []` を指定する。
- ツール呼び出し不可をAPIレベルでも保証する。

ランタイム提供の認証対応APIを優先し、互換性が必要な場合はフォールバックを用意する。

### 6.4 ツール結果

成功時にはAdvisorのテキストを返す。

付加情報として以下を保持する。

- `advisorModel`
- `effort`
- `usage`
- `stopReason`
- `errorMessage`

結果形式は可能な限り元実装と互換にする。

エラーはExecutorのターンをクラッシュさせず、通常のツール結果として返す。

対応するエラーは以下を含む。

- Advisor未設定
- モデルが存在しない
- 認証情報が利用できない
- API呼び出し失敗
- 呼び出し中断
- 空応答
- 予期しない例外

正常終了した空応答は最大1回再試行する。

APIエラーとキャンセルは無条件に再試行しない。

### 6.5 /advisor コマンド

`/advisor` を実行すると、モデル選択UIを表示する。

機能要件：

- 認証済みの利用可能なモデルを列挙
- モデル名・プロバイダー名・モデルIDで検索
- ファジー検索に対応
- キーボード操作に対応
- 現在選択中のモデルを識別可能
- `No advisor` による無効化
- 思考対応モデルでは思考量を選択
- `high` を推奨値として表示
- 設定変更後に保存と有効化を実行
- Esc操作によるキャンセル
- 非対話環境では適切なエラー通知

元実装のUI操作（最大10行表示、上下キー、Enter、Esc、Backspaceなど）を基本的に再現する。

思考量の選択画面でEscを押した場合は、元実装に合わせてモデル選択自体を維持し、思考量未指定として保存する。

### 6.6 動的な有効化・無効化

対象イベント：

- `session_start`
- `before_agent_start`
- `model_select`
- `thinking_level_select`

イベント発生時に設定と現在のExecutorモデルを参照し、ツールの有効状態を再評価する。

有効化・無効化には `getActiveTools()` と `setActiveTools()` を使用する方式を基本とする。

注意事項：

- 他の拡張機能のツールを削除しない。
- 同じツールを二重登録しない。
- モデル変更時に即座に状態を反映する。
- 思考量の変更にも追従する。
- 利用できないAdvisorモデルが設定されている場合は安全に無効化する。
- セッション復元時の通知が繰り返されないようにする。

## 7. standardモードのプロンプト仕様

### 7.1 最適化対象

Executorのシステムプロンプトへ追加される以下の情報を対象とする。

- ツールのdescription
- `promptSnippet`
- `promptGuidelines`
- その他、拡張機能が常時追加する指示

Advisor自身に送信するシステムプロンプトは別管理とする。

### 7.2 ツール説明

ツールの入出力仕様を短く説明する。

含める情報：

- 高性能モデルへ相談するツールであること
- 会話履歴が自動転送されること
- 引数が不要であること
- 助言を受けた後に作業を再開できること

詳細な呼び出し条件は、原則として `promptGuidelines` 側へ集約する。

### 7.3 行動指針

元実装の7項目が担う判断条件と例外条件を保持する。

最初の候補として、以下の英語ガイダンスを評価する。

1. "Call `advisor` before substantive work or major decisions; routine orientation and obvious reactive steps do not require consultation."
2. "Call `advisor` before declaring completion, after making the deliverable durable."
3. "Consult when stuck, facing repeated failures, or considering a different approach."
4. "For multi-step tasks, consult at least before committing to an approach and before finishing; avoid redundant calls on short, obvious steps."
5. "Give advice serious weight unless contradicted by empirical results or primary evidence; a passing self-test alone does not invalidate a concern."
6. "If advice conflicts with evidence already gathered, reconcile the conflict with another consultation rather than silently changing direction."
7. "Summarize each advisor result's key guidance in the next visible user-facing reply."

これは確定版ではなく、比較テスト用の初期候補とする。

### 7.4 プロンプト最適化の評価

少なくとも以下を比較する。

- Original：元実装のガイダンス
- Standard：最適化後のガイダンス

比較時には、ガイダンス以外の条件を同一にする。

計測対象：

- 拡張機能による追加トークン数
- 必要な場面でAdvisorを呼び出した割合
- 不要なAdvisor呼び出しの割合
- 重要な判断前の相談漏れ
- 完了前の相談漏れ
- Advisor助言の反映率
- 最終タスクの品質
- Advisor呼び出し回数と費用

トークン数は、Piが実際に構築したシステムプロンプトを可能な限り取得して計測する。

API上で取得できない場合は、モデル対応のトークナイザー等による推定値であることを明示する。

### 7.5 品質の合格基準

**プロンプト削減率よりAdvisor呼び出し精度を優先する。**

- 重大な相談漏れが新たに発生しないこと。
- 必須相談シナリオの呼び出し再現率が、元実装の観測結果を下回らないことを目標とする。
- 不要な呼び出しが著しく増加しないこと。
- Advisor結果の利用方法が元実装より悪化しないこと。
- 最終タスクの品質に明らかな劣化がないこと。

モデル応答には非決定性があるため、単発テストで同等性を断定しない。

比較結果が不安定な場合は試行回数を増やす。

品質基準を満たせない場合は、削減した指示を段階的に戻し、呼び出し精度を優先する。

プロンプト品質テスト：

次のようなシナリオを用意する。

1. 単純な情報取得：原則として相談不要
2. 作業前のファイル探索：原則として相談不要
3. 複雑な実装方針決定：相談が必要
4. 複数候補のアーキテクチャ選択：相談が必要
5. 前提条件が曖昧な実装：相談が必要
6. 繰り返すテスト失敗：相談が必要
7. アプローチの変更判断：相談が必要
8. セキュリティ上の重大な判断：相談が必要
9. 作業途中の明白な次ステップ：重複相談不要
10. 実装完了後の最終確認：相談が必要
11. Advisorの助言と観測結果の矛盾：再相談が必要
12. Advisor呼び出し後の助言反映：指示に沿った作業継続が必要

最低限、元実装とstandardそれぞれで複数回の試行を行う。

特に軽量Executorモデルでの呼び出し精度を重視する。

比較結果はシナリオごとに記録する。

## 9. 実装時の注意事項

### 9.1 元実装との互換性

参考実装は `@earendil-works/pi-coding-agent` などのフォーク版SDKを利用している。

標準Pi環境へ移植する場合は、APIの存在と仕様を確認してから実装すること。

未確認のAPIが存在する前提でコードを書かないこと。

### 9.2 セキュリティ

Advisorには会話履歴・ツール結果が転送される。

異なるプロバイダーのモデルを選ぶ場合、機密情報が別のモデル提供元へ送信される可能性があるため、READMEで明示する。

- APIキーや認証情報をログへ出力しない。
- 会話履歴を独自にファイル保存しない。
- デバッグログには原則としてモデル名・トークン数・処理結果などのメタデータだけを記録する。
- Advisorによるツール実行を許可しない。

### 9.3 コスト

Executorの常駐プロンプトとAdvisorへの会話履歴転送は、別々に評価する。

常駐プロンプトが削減されても、Advisor呼び出し時のAPIコストは発生する。

既定では会話履歴を省略せず、呼び出し品質と機能互換性を優先する。

コスト削減のための履歴省略は、品質を確認したうえで別途検討する。

### 9.4 キャッシュ

ツール一覧のJSONは安定した順序でシリアライズする。

内容が変化していない場合、同じ文字列を生成することでプロンプトキャッシュの再利用を促進する。

キャッシュの無効化条件には、ツール名だけでなく説明とパラメータ定義の変更も考慮する。
